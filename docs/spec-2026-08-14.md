# cyncd — Phase 1 spec

**Source:** `CYNCD meeting 14.08.2026.pdf` (stakeholder notes), plus decisions
taken 2026-08-24.
**Status:** six questions answered, five still open (§14). One open question
does not block anything on the critical path.

This document is written to be read cold. §0 is context for someone who has
never seen the repo; skip it if you have.

Notation: **[NOTES]** is from the stakeholder document, quoted or closely
paraphrased. **[DECIDED]** was confirmed by the stakeholder, with the date.
**[REC]** is a recommendation from this document, not yet approved.
**[OPEN]** still needs an answer.

## 0. Context

### 0.1 What cyncd is

A relationship app for couples. It reads one partner's menstrual cycle and
personal patterns, and turns them into daily guidance that **both** partners
see — framed for each of them. The premise is shared understanding: they are
looking at the same day from two perspectives, not two different apps.

Two users, referred to throughout as **Her** and **Him**. In the codebase these
are `Role = 'shanice' | 'darnell'` — the demo couple's names, used as the role
identifiers so a screen never has to map a name onto a role. Display strings
come from `ROLE_NAMES` and `ROLE_LABELS` in `src/content/index.ts`; do not
hardcode either name in a component.

### 0.2 Repo state

An Expo (SDK 57) / React Native app, ported in August 2026 from a Vite web
prototype that lives at `../synched-prototype`. The port is complete and
committed. The web prototype is **reference only** — do not edit it, but it is
useful for seeing how something used to work.

```
src/
  app/          expo-router routes. Deliberately ONE route (see 0.3)
    _layout.tsx   providers only
    index.tsx     the whole app: state-based screen switching
  content/      the data layer — guidance copy, coach graph, onboarding, types
  state/        store, reducer, derived selectors, AsyncStorage persistence
  screens/      8 screens
  components/   8 components + ui.tsx (shared primitives)
  theme/tokens.ts  design tokens, ported from the prototype's CSS
docs/
  spec-2026-08-14.md   this file
```

117 tests pass across 7 files (`npm test`, vitest). They cover the content and
state layers only — plain TypeScript, no renderer.

### 0.3 Architecture decisions already made

Do not undo these without a reason; each was deliberate.

**Routing is state, not a router.** `src/app/index.tsx` switches on
`state.flow` and a `tab` local. Four tabs plus a linear onboarding flow do not
need a navigation graph, and it keeps notification deep-links to a single
`setTab` call. There is one expo-router route.

**Storage is async, so the store hydrates in an effect.** `CyncdProvider` mounts
on `initialState()` and dispatches `hydrate` once AsyncStorage returns. The save
effect is gated on a `hydrated` flag — without that guard, the mount-time write
would erase stored data before `load()` read it. `hydrated` is exposed on the
context; anything that would look wrong for a tick should wait on it.

**`reconcile()` is forgiving on fields and strict on version.** A missing field
falls back to its initial value; a version mismatch starts clean. Malformed
array records are dropped individually with a `console.warn` rather than
silently. Rationale: a white screen is the worst possible failure.

**The palette is fixed and light.** A dark scheme would be a second design
system. `userInterfaceStyle` is `"light"` in `app.json`.

### 0.4 Tooling and conventions

- `npm run verify` — typecheck + tests. Runs automatically on every commit via
  `.githooks/pre-commit` (wired through `core.hooksPath`, so it is shared).
- **Read `AGENTS.md` before doing any rename.** Three find-and-replace passes
  have shipped breakage in this repo; the file documents each incident. The
  short version: use scope-aware rename-symbol, never text replacement, and
  never replace across a third-party API surface.
- Expo SDK 57 specifically — read
  `https://docs.expo.dev/versions/v57.0.0/` before writing platform code.

### 0.5 Deferred work

`src/state/__deferred__/store.test.tsx` — 253 lines of provider behaviour tests
that were passing in the web build and are not ported. They need
`@testing-library/react-native` plus a jest-expo project. See the README beside
them. This is known debt, not dead code.

## 1. What this spec changes

The 14.08 meeting is a re-spec, not a revision list. Measured against the
ported app:

- One entirely new screen — **Forecast/Track**, Her only.
- One new cross-cutting feature — the **cyncd Score** — appearing on four
  screens.
- Three of four existing screens change their underlying model: **Partner**
  inverts from derived to user-controlled, **Plan** gains a calendar,
  **Reflect** becomes conversational.
- Navigation becomes asymmetric between the two users.
- The scripted 7-day week is retired in favour of a cycle model (§5).

Only **Today** survives largely intact, gaining the Score preview.

## 2. Blocking: the content lint

`src/content/content-rules.test.ts` currently forbids most of the vocabulary
this spec requires:

```ts
const BANNED = [
  'hormone', 'hormonal', 'menstrual', 'ovulat', 'luteal', 'follicular', 'pms',
  'symptom', 'diagnos', 'medical', 'clinical', 'therapy', 'treatment', 'disorder',
  'chart', 'graph', 'score',
  'streak', 'badge', 'you missed', "don't forget", 'keep it up',
]
```

plus a rule that `cycle` appears nowhere outside onboarding.

**[NOTES]** require `cyncd Score`, `Current menstrual cycle phase`, `Cycle day`,
and `Physical symptoms` / `Emotional symptoms` as tracker fields. All fail today.

The rules are right about the *audience* and wrong about the *scope* — the
notes independently insist the partner *"must not automatically see: her cycle
day, her menstrual phase, symptoms she has logged."*

**[REC] Rescope by audience:**

| Surface | Clinical + cycle vocabulary |
|---|---|
| Her Forecast / Track (private) | **Allowed** — it is a tracker; refusing the words makes it useless |
| Today, Partner, Plan, Reflect, notifications, Score copy | **Banned** — unchanged |

1. Split into `BANNED_EVERYWHERE` and `BANNED_IN_SHARED`.
2. Remove `'score'` entirely.
3. Add the notes' own prohibitions to `BANNED_EVERYWHERE`: `bad day`,
   `low compatibility`, `relationship risk`, `difficult phase`,
   `hormonal behaviour`, `she may be emotional`, `avoid her today`.
4. Replace the blanket `cycle` rule with one scoped to shared surfaces.
5. Relax the 14-sentence verbatim lock (§5.2), keeping every other rule.

**Nothing else can start until this lands** — the suite rejects the new content.

## 3. cyncd Score

**[NOTES]** A daily percentage showing how naturally aligned the couple may
feel that day and how much intentional care may help them connect. Playful,
emotionally intelligent, shareable.

> It is not a compatibility test and it does not measure whether the
> relationship is good or bad.

### 3.1 Calculation

**[NOTES]** Phase 1 needs no advanced AI. Rule-based, from: her cycle day and
predicted phase, predicted mood and emotional sensitivity, predicted energy and
social capacity, expected communication style, recent accuracy feedback,
feedback submitted separately by each partner, and completion of the suggested
shared action.

| Weight | Component | Seeded by |
|---|---|---|
| 40% | Predicted communication alignment | Onboarding (both) + phase |
| 30% | Emotional and energy compatibility | Onboarding (both) + phase |
| 20% | Shared action or check-in completion | Behaviour |
| 10% | Recent accuracy feedback | Behaviour |

**[NOTES]** *"This calculation can be adjusted technically if there is a clearer
or more reliable way to produce the same user experience."*

**70% of the Score is seeded at onboarding, and half of that seed is his** —
"alignment" cannot be computed from one person. This is why his question set
changes in §7.

**[REC]** A pure function in `src/content/score.ts`, unit-tested per band. No
model call.

### 3.2 Categories and language

| Band | Label | Line |
|---|---|---|
| 80–100% | Naturally aligned | Connection and communication may feel more natural today. |
| 60–79% | Gently connected | There is good potential for connection, but thoughtfulness may make the difference. |
| 40–59% | Different rhythms | Both users may need different things today, so clear communication will be important. |
| Below 40% | Extra-care day | Patience, reassurance or personal space may be especially helpful. |

**[NOTES]** *"A lower score should always be followed by practical guidance so
that the user knows what to do with the information."*

**[REC]** Enforce as a lint rule: every band carries a non-empty action string.

### 3.3 Confidence wording

**[NOTES]** Wording differs before and after enough feedback has been
collected; the demo should communicate that the score becomes more accurate and
individual over time.

**[OPEN]** The two wordings were described but not captured. Needs exact copy.

### 3.4 Placement

| Screen | What appears |
|---|---|
| **Her Home** | Preview beneath her main daily insight: percentage, status, one line, button to the full score. Her cycle information stays separate. |
| **His Home** | The same preview, focused on practical relationship meaning rather than her private cycle information. |
| **Partner** | The **full** score: large percentage, category, explanation, completed-action button, expandable detail, sharing option, recent history. |
| **Plan** | Upcoming *predicted* score to pick better days — "High-connection day", "Good day for a date", "Keep plans flexible", "Extra-care day", "Good day for an important conversation". Supports the calendar without taking it over. |
| **Reflect** | End of day, one quick question. A slider or five simple options. Answers influence future scores. |

**[NOTES]** Both partners see the same overall score; private responses stay
separate unless shared.

### 3.5 Sharing

**[NOTES]** A premium branded card shareable to Instagram Stories, WhatsApp,
TikTok and elsewhere.

**[REC]** `expo-sharing` + `react-native-view-shot` over an off-screen view. The
card carries score, band and branding — **never** cycle data. Test that.

### 3.6 Product rule

**[NOTES]**, quoted in full because it governs everything above:

> The cyncd Score measures the connection conditions surrounding the couple
> that day. It does not measure the quality, health or future of their
> relationship. Every score must lead to understanding and a useful action. It
> should never create blame, fear or judgement.

## 4. The cycle model — the keystone

**[DECIDED 2026-08-24]** The scripted 7-day week does **not** survive. Content
is tailored to her and her cycle; the script existed only for the initial demo.

Everything downstream reads from a cycle model rather than a day index:

```
cycle model ──┬── Today guidance (phase-driven)
              ├── cyncd Score (its first two components — 70% of the weight)
              ├── Forecast screen (displays it directly)
              └── Plan suggestions (predicted good days)
```

### 4.1 Model vs tracker

**[REC] These are separable, and only the first is on the critical path:**

| | Cost | Needs |
|---|---|---|
| **Model** — `(lastPeriodStart, cycleLength, today) → { phase, cycleDay, nextPeriod, sevenDayOutlook }` | ~1 day | Nothing. Seeds from onboarding |
| **Tracker** — the §6.2 log UI, retroactive editing, prediction that learns | Weeks | The model + real storage |

Build the model first, standalone and unit-tested. It unblocks the Score,
Today, and a read-only Forecast with no tracker UI in existence. The tracker
then improves the model's inputs rather than gating anything.

### 4.2 Degradation when cycle data is absent

Cycle questions stay skippable (§7.3). The model must therefore have a defined
answer for "no cycle data":

- Score runs on its trait components only, and says it is still learning.
- Forecast shows an invitation to log a first period rather than a phase.
- Today falls back to trait-driven guidance — the role `STARTER_NOTE` plays
  today.

**[REC]** Model this explicitly as a discriminated union rather than nulls, so
no consumer can forget the case.

## 5. `days.ts` — what happens to it

### 5.1 Re-key, do not delete

538 lines, currently the **only** content the app has. Deleting it before
phase-keyed replacement content exists leaves the app mute.

**[REC]** The guidance is keyed by day index 1–7. Re-key by **cycle phase** —
which is what it was always approximating — and it becomes seed content for the
model-driven build.

### 5.2 The verbatim lock

`content-rules.test.ts` locks 14 spec-mandated sentences verbatim. Those were
the *demo* spec, and the demo is over, so the lock is obsolete.

**[REC]** Relax that specific lock; keep every other rule in the file. The
verbatim lock protected wording; the rest protects users, and only the first is
outdated.

## 7. Onboarding

**[DECIDED 2026-08-24]** Question sets below are approved, including the
reframing and the change to his set.

### 7.1 Reframing: variation, not fixed traits

The old questions assumed a static person — *"What is your general energy
level?"*. The app's premise is that days differ, so the questions now ask about
**variation over time**. This also primes the user for what the app is for.

### 7.2 Her set — 7 questions

| # | Prompt | Options | Feeds |
|---|---|---|---|
| 1 | How does your energy usually change across the month? | Fairly steady · Some ups and downs · Big swings | Score 30% |
| 2 | When you're feeling stretched, what usually helps? | Space · Reassurance · Practical help | Score 40%; **pairs with his Q3** |
| 3 | When something comes up between you, what do you prefer? | Talk it through soon · Need time first · Depends on the day | Score 40% |
| 4 | How do you usually like to spend a free evening? | At home · Out · Depends | Score 30% (social capacity) |
| 5 | When did your last period start? | date | **Cycle model** |
| 6 | How long is your cycle usually? | ~28 days · Shorter · Longer · Varies · Not sure | **Cycle model** |
| 7 | When do you usually have time together? | Weekdays · Weekends · Varies | Plan suggestions |

**Removed:** *sleep* — the notes list it as a **tracked** field (§6.2), where it
is measured rather than self-reported. *Mood shifts* — this is what the app
should tell her, not ask her; the tracker measures it.

**Added:** cycle length. The model cannot run without one; "Not sure" defaults
to 28 days until the tracker learns better.

Question 2 deliberately shares its option set with his Q3, which is what makes
"does he offer what she needs?" computable rather than guessed.

### 7.3 Cycle questions stay skippable

**[DECIDED 2026-08-24]** Confirmed.

Asking for a period date at first launch — before the app has demonstrated
value — is a known drop-off point and a trust ask that has not been earned at
that moment. The existing principle (everything skippable, `STARTER_NOTE`, no
guilt) holds, and the notes reinforce it: *"never create blame, fear or
judgement."*

What changes is the **framing**, not the optionality. Currently it is buried
last and phrased apologetically:

> "Approximate cycle start date? Optional — skip if you would rather not."

**[REC]** Ask it properly: state plainly what it unlocks and that it stays
private. Re-offer it later from the Forecast screen, so a skip is not a one-shot
loss. Degradation is specified in §4.2.

### 7.4 His set — 5 questions

**[DECIDED 2026-08-24]** Approved.

His current four questions are all about *supporting her* — none establish his
own baseline, so there is nothing to compute alignment against. Three of the
five now mirror hers.

| # | Prompt | Options | Change |
|---|---|---|---|
| 1 | How would you describe your usual energy? | Low · Moderate · High | **New — mirrors her Q1** |
| 2 | When something comes up, what do you prefer? | Talk immediately · Need time first | **New — mirrors her Q3** |
| 3 | How do you usually support your partner? | Talk · Space · Practical help | Kept — pairs with her Q2 |
| 4 | How do you like to spend a free evening? | At home · Out · Depends | **New — mirrors her Q4** |
| 5 | What causes most misunderstandings between you? | Timing · Communication · Energy | Kept |

**Removed:** *preferred time for serious conversations*, *planning comfort* —
neither feeds the Score, and his set should stay short.

### 7.5 Implementation notes

- `ONBOARDING_QUESTIONS` and `PARTNER_QUESTIONS` are in
  `src/content/onboarding.ts`; the shared `QuestionFlow` screen renders both.
- **Answers are keyed by question `id`** in `state.onboarding.answers`. Changing
  an existing `id` orphans stored answers. Where a question is conceptually the
  same, keep the id (`energy`, `communication`, `social`, `routine`); use new
  ids for genuinely new questions (`cycleLength`, and his `energy` /
  `communication` / `social`).
- `SCHEMA_VERSION` in `src/state/persistence.ts` must be bumped.
- `QuestionFlow` already supports `kind: 'date'`. Cycle length is a chip
  question, so no new input kind is needed.

## 8. Changed screens

### 8.1 Today — both users

**[NOTES]** Remains the main Home screen for both; the main daily quote appears
prominently for both. Each side gets: the daily quote, gentle reminders about
app setup at the top of the screen, a relevant relationship insight, and a
simple suggestion or action. Her information can be slightly more personal
because cyncd works directly from her tracked information.

> **IMPORTANT** — I want these screens to visually match. They are looking at
> the same day and the same relationship, just from their individual
> perspective.

**Gap:** the Score preview is new; the "gentle reminders" slot is new and
distinct from the existing notification banner. Otherwise Today is close.

### 8.2 Partner — both users, shared space

**[NOTES]** *"Rather than cyncd automatically showing everything about Her to
Him, this gives both users control over what they choose to share."*

- **Shared with me** — what their partner chose to share: feelings, notes and
  messages, relevant insights, important information, needs and preferences,
  things they want their partner to understand.
- **Shared by me** — what I chose to share, ability to edit or remove, choose
  what stays private.

**[NOTES]** She could share a particular insight from her Forecast. He can share
back. This must **not** become a messaging replacement — it is a controlled
bridge, and the data feeds their prediction over time.

**Gap:** an inversion. The app currently *derives* what he sees, gated by a
single global `sharing.paused` boolean. The spec wants **per-item,
user-initiated sharing with edit and revoke**. The boolean becomes a collection.

### 8.3 Plan — both users

**[NOTES]** Three stacked sections:

1. **Shared sticky-note calendar** — visual and clean, both contribute. Plans,
   dates, saved activities, important events, cyncd colour indicators, suggested
   good days, sticky notes from either partner. Icons for special events in a
   date's top-right corner. Link Google / Apple / Outlook calendars.
2. **cyncd suggestions** — timing-based, e.g. *"Saturday — Date Night"*.
   Actions: Save · Add to Calendar · Share.
3. **Ask cyncd** — a simple chatbox, *"directly inside Plan rather than making
   another screen"*. Uses Forecast + shared information + existing plans +
   previous feedback.

**[DECIDED 2026-08-24]** There is **one assistant, accessible across the whole
app**. Plan gets an entry point because that is where it is most convenient. It
is not a second, Plan-only chatbox, and the user should never have to navigate
to a dedicated chat destination.

**[REC]** The existing architecture is already right: `CoachSheet` is a global
modal owned by the app shell. The work is (a) an entry point on Plan, (b) keep
the Today entry, (c) eventually replace the scripted chip graph with free text.
Do **not** build a separate component inside Plan.

**Gap:** the calendar is entirely new.

### 8.4 Reflect — both users

**[NOTES]** *"I want this to feel much more natural."* cyncd opens with something
simple and the user types. It understands, responds appropriately, and logs
useful signals in the background. It may ask **one** relevant follow-up
*"rather than presenting ten questions."*

> Prediction → Real experience → Reflection → cyncd learns → Future guidance
> improves

**Gap:** currently a slider, mood chips and a timeline. Note the tension with
§3.4, which puts one quick structured Score question here — so Reflect is
conversational **and** carries one slider-or-five-options question.

### 8.5 Welcome / splash screen

**[NOTES]** A small transition page to make opening cyncd feel intentional
rather than transactional. Shows the wordmark line — *"Stay in cyncd. Know the
day together."* — a Continue affordance, and their current quote (e.g. *"A
connection day / Thoughtful gestures may go a long way today."*). Around two
seconds before revealing the Home screen.

**[DECIDED 2026-08-24]** This is the **splash screen** — it appears anywhere a
splash would naturally appear, i.e. on launch. Not once after onboarding.

**[REC]** App-lifecycle, not a `Flow` state, and it fills a gap that already
exists. `src/app/index.tsx` renders an empty frame while storage hydrates:

```tsx
if (!hydrated) return <View style={styles.frame} />
```

That becomes the Welcome screen. The dwell is time already being spent, and the
quote it shows needs hydration to have finished anyway — so the sequencing is
free rather than an artificial delay. Hold a minimum display time so a fast
hydrate does not flash.

**Naming collision:** the `Flow` union already has a member `'splash'` — the
pre-signup landing screen with the Create account button, a different thing.
Rename it (`'landing'`) when this is built, or the state machine reacquires the
ambiguity `'paired'` just had.

## 9. Navigation and perspective switching

### 9.1 Asymmetric tabs

**[NOTES]**

| Her | Him |
|---|---|
| TODAY — daily cyncd insight | TODAY — daily cyncd insight |
| **FORECAST** — her cycle, symptoms, tracking and future outlook | — |
| PARTNER — what we choose to share | PARTNER — what we choose to share |
| PLAN — our calendar, suggestions and planning AI | PLAN — our calendar, suggestions and planning AI |
| REFLECT — tell cyncd what actually happened | REFLECT — tell cyncd what actually happened |

**Gap:** `src/content/index.ts` exports one flat `TABS` array used by both. It
becomes a function of role, and `TabId` gains `'forecast'`.

### 9.2 Perspective switching stays

**[DECIDED 2026-08-24]** At this stage the app must still be able to **switch
between the His and Hers perspectives**.

This is currently the role toggle in `src/components/DemoBar.tsx` — a
collapsible presenter's panel in the top corner with a role toggle, a day
stepper and a reset. It survives this phase. There are no real accounts yet;
one device shows both sides.

Three consequences that are easy to get wrong:

**Switching role must reconcile the active tab.** She can be on Forecast; he has
no Forecast. Switching to him while that tab is active would render nothing.
**[REC]** On role change, if the active tab is not in the new role's tab set,
fall back to `'today'`.

**`openNotification()` must never deep-link him to Forecast.** It returns a
`TabId` for the shell to navigate to. A notification targeting `'forecast'` is
meaningful only for her. **[REC]** Either scope notifications by role, or have
`openNotification()` return `null` when the target is not in the current role's
tab set.

**The day stepper needs rethinking.** It currently steps a 1–7 index into the
scripted week. With the script retired (§4), there is no such index. **[REC]**
It should step the **simulated date**, which advances cycle day through the
model — preserving the demo affordance while working with the new content
source. This is the one part of `DemoBar` that the cycle model breaks.

## 10. Data model changes

Beyond the ported `CyncdState`:

| Addition | Shape | Notes |
|---|---|---|
| Cycle seed | `{ lastPeriodStart, cycleLength }` | From onboarding; both optional |
| Cycle log | Per-day entries covering §6.2 | Hers, private, retroactively editable |
| Cycle prediction | Phase, cycle day, next period, 7-day outlook | Derived — not stored |
| Score | Daily percentage + band + action + history | Derived; history is shared |
| Shared items | `{ id, author, kind, body, sharedAt, revoked }` | Replaces `sharing.paused` |
| Calendar entries | `{ id, date, title, kind, author, icon? }` | Both authors + external links |
| Reflection transcript | Free text + extracted signals + the one structured answer | Replaces `{ accuracy, mood }` |
| Per-user feedback | Separate per partner, private by default | Feeds the Score's 10% and 20% |

`SCHEMA_VERSION` must be bumped and `reconcile()` given guards for every new
collection.

**Known latent bug worth fixing in the same pass:** `reconcile()` casts
`raw.flow` to the `Flow` union **without validating it**
(`src/state/persistence.ts`, ~line 137). A stored value no longer in the union
is accepted and then matches no screen — a blank frame. This spec adds and
renames `Flow` states, which makes it reachable.

## 11. Where AI is, and is not

| Feature | Implementation |
|---|---|
| cyncd Score | **Rule-based.** Explicitly *"does not require advanced AI"* |
| Forecast prediction | **Statistical**, over her logged data |
| Daily quote / insight / suggestion | **Authored content**, selected by phase and score |
| **Reflect** | **Model.** Free text in, understanding + one follow-up out |
| **Ask cyncd** | **Model.** Grounded in Forecast + shared info + plans + feedback |

Two model surfaces, both conversational, both needing §2's rules enforced at
**runtime**, not only at build time. Everything else is deterministic — cheaper,
testable, and demonstrable without a network call.

## 12. Privacy rules

**[NOTES]** Both partners see the shared Score, but the partner must **not**
automatically see: her cycle day, her menstrual phase, symptoms she has logged,
private notes, her individual feedback, or anything she has not chosen to share.

> The score should translate the relevant information into relationship
> guidance without exposing private health or cycle data.

**[REC]** The most testable requirement in the document, and the most damaging
to get wrong. Enforce as a boundary, not a convention:

1. Partner-facing state is derived through **one** function. Nothing else reads
   the cycle log.
2. A test asserts no partner-facing string contains cycle vocabulary — across
   every phase and every score band.
3. A test asserts the share card contains no cycle data.

Note this interacts with §9.2: the perspective switch means one device holds
both sides, so the boundary is enforced in *derivation*, not by access control,
until there is a backend.

## 13. Build order

Revised after the 2026-08-24 answers. The cycle model moved to the front:
with the scripted week retired, the Score and Today both read from it.

| Stage | Work | Why here |
|---|---|---|
| **0** | Rescope the content lint (§2); relax the verbatim lock (§5.2) | Blocks all new content |
| **1** | Onboarding question sets (§7) | Seeds the model; small; no dependencies |
| **2** | **Cycle model** — pure functions, unit-tested (§4) | Keystone. Score and Today read it. ~1 day |
| **3** | cyncd Score: calculation, bands, copy, Today preview, full Partner view | Headline feature. Still no backend |
| **4** | Re-key `days.ts` by phase; Today driven by the model (§5.1) | Retires the script without leaving the app mute |
| **5** | Tab asymmetry + role-switch reconciliation (§9); Forecast read-only | Her/Him split lands; no tracker UI needed |
| **6** | Track/Log (§6.2); prediction improves | The long pole. Everything above works without it |
| **7** | Partner rebuild: per-item sharing, edit, revoke | Needs insights worth sharing |
| **8** | Plan: calendar, then the assistant entry point | Calendar independent; assistant needs 2–6 to ground |
| **9** | Reflect: conversational rewrite | Needs the model surface and guardrails proven |
| **10** | Welcome/splash (§8.5), share card | Small, self-contained, high polish |

Stages 0–3 are roughly a week and demo well alone. Stage 6 is the long pole and
is now genuinely deferrable.

**Where a backend fits.** Nothing before stage 7 requires Supabase — stages 1–6
are local computation over data the app already collects, and §9.2 keeps both
perspectives on one device. Stage 7 is the first that cannot work without a
server: per-item sharing between two people on two devices *is* shared state.
Design the schema after stage 6, when the cycle log's shape is settled by having
built it.

**Exception:** if two real people need to test on two devices before then, the
backend moves to the front regardless.
